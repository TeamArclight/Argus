# ARGUS Backend Database Migrations Guide

This directory manages database schema migrations for the ARGUS API backend using [Alembic](https://alembic.sqlalchemy.org/).

---

## 1. Overview & Architecture

- **Engine & Config**: Alembic reads runtime database configuration dynamically from `app.core.config.settings.DATABASE_URL`.
- **Target Metadata**: Autogeneration references `app.db.session.Base.metadata`, covering all domain models in `app.models.domain`.
- **Production Safety**: Application startup (`app.main.lifespan`) does **NOT** execute implicit schema creation or migration calls. Database migrations are an explicit deployment responsibility.

---

## 2. CLI Migration Commands

All commands should be executed from the `services/api` directory:

### Fresh Database Setup
To initialize a fresh database with the baseline schema:
```bash
alembic upgrade head
```

### Adopt Existing Phase-4 Database
If deploying against an existing development or staging database where the schema already physically exists:
1. Back up your database.
2. Verify the schema matches current domain models.
3. Stamp the current baseline revision without re-executing DDL:
   ```bash
   alembic stamp head
   ```
4. Verify active version:
   ```bash
   alembic current
   ```

### Check Current Migration Status
```bash
alembic current
```

### View Migration History
```bash
alembic history --verbose
```

### Create a New Migration Revision
After modifying SQLAlchemy models in `app/models/domain.py`:
```bash
alembic revision --autogenerate -m "description_of_changes"
```
*Note: Always inspect the autogenerated revision script in `alembic/versions/` before committing.*

### Rollback Migration
Roll back the most recent migration step:
```bash
alembic downgrade -1
```

---

## 3. Programmatic Execution & Deployment Sequence

A helper script is provided at `services/api/scripts/migrate.py` to run migrations programmatically:

```bash
python scripts/migrate.py
```

### Recommended Production Deployment Sequence
1. Backup target database.
2. Execute schema migrations:
   ```bash
   alembic upgrade head
   ```
3. Start API web server:
   ```bash
   uvicorn app.main:app --host 0.0.0.0 --port 8000
   ```

---

## 4. Design & Governance Decisions

### `run_id` Nullability Constraint Policy
- In Phase 4, `run_id` foreign keys (`VerificationResult.run_id`, `RuleEvaluation.run_id`, `RiskSignal.run_id`) were introduced with `nullable=True` to preserve compatibility with existing un-scoped historical data.
- The baseline migration (`baseline_argus_schema`) preserves `run_id` as `nullable=True`.
- **Constraint Policy**: `run_id NOT NULL` enforcement is explicitly deferred until data backfill and controlled production rollout are completed.

---

## 5. Security & Safety Rules

- **No Hardcoded Credentials**: Database connection strings are resolved strictly via environment variables / `settings.DATABASE_URL`. `alembic.ini` contains no credentials.
- **SQLite Batch Mode**: Alembic is configured with `render_as_batch=True` for SQLite environments to support table alterations during testing and local development.
- **Backup Mandatory**: Always create a full database snapshot before running migrations in production.
